# Evidence discipline for issues, PRs, and comments

Whether a claim is **true**, as distinct from how it is written — that is `PROSE-DISCIPLINE.md`'s job, and these two were one file until 2026-09-04, when the evidence half had grown to 48% of a document titled for style.

**Apply these whenever you cite a number or write a correction** — drafting a body is the common case, not the trigger. A figure quoted in a commit message, a cross-session message, or a doc comment needs the same checks and gets them less often.

**Budget.** This is the half that grows: ten consecutive kaizen commits to this repo added 166 lines and deleted 7, and nearly all of it landed here. Prefer a change that is roughly line-neutral — a new rule can usually pay for itself out of the previous rule's justification prose. Keep the clause that makes a measured example undeniable; cut the parameter-space texture around it.

## Before citing a measurement

A number in an issue body licenses work. Before one goes in, establish what its presence in a file does not establish on its own.

- **Is it derived from the data, or from the configuration?** A field can vary across runs, carry a plausible name, and still be a restatement of the flags. Measured on `matsengrp/phyz` 2026-09-02: `--summary-tsv`'s `search_rounds` read exactly 42 in all 43 cells of a sweep, because it resolved to `max_failures + free_pool_slots` — inputs the operator had chosen. It looked like search depth and was an echo of the command line. The cheap tell is to predict the value from the flags alone before opening the file; if you can, it is not evidence. A field that varies with `num_leaves` is the harder case, because tracking one input looks more like measurement than tracking none.
- **Does it reach disk, where a reader can open it?** Four separate times in one day the answer was no, in four different ways: a cited `results/raw/` path was gitignored and absent from a fresh clone; the stderr files holding an experiment's primary evidence matched no `*.tsv` negation at any depth; a harness discarded the subprocess stdout carrying the column it was there to collect; and a rescued copy lived at a path nothing committed referenced. Each was invisible in the same way — the run produced the quantity, and nothing that survived the run recorded it. **Sender-side: when you hand a figure to someone who may cite it, state its path — or state that it has none.** Three of one night's retracted numbers crossed a session boundary first; the relay is where a claim acquires the relayer's authority without acquiring any of its evidence.
- **A rule that exists and is not applied is a different problem from a missing one, and it is the one this file has.** Measured on `matsengrp/phyz` 2026-09-12: repeatedly in one night, a check returned a clean negative without having read its input, several of them reaching or nearly reaching a verdict — and **every one had a written rule in this file sitting unapplied behind it** — the grep-the-claim's-subject rule below, and "a detector's negative is not evidence until the detector is shown to fire." A fourth phrasing of either would have been the least useful response available. **Before adding a rule here, check whether the one you need is already present and simply did not fire.** The single mechanism from that night genuinely absent here is also the worked example for why non-application is the norm rather than the exception: **a sign convention lives in a metric's *definition*, while the sentence interpreting it is written from the *values*, so every check that compares figures passes while the prose inverts.** A `defect_count` (lower is better) was defined with that convention stated explicitly, inverted in two sentences of one commit, passed two independent gate reviews — and was then written backwards a **third** time into the very sentence repairing the first two, by an author who had the convention in mind and had been corrected on it minutes earlier. Nobody misremembered it. **State the convention where you cite the number, not only where you define it.**

- **Is it a census, or the items you already had?** Re-derivation validates the members of a set and cannot find a missing one — every item checks out and the count is still wrong. For any "which items have property P" claim, derive the population from P rather than from familiarity, then evaluate P on every member: if P is "merged before commit X," the population is every merge, not the issues you can name. **Listing the population is not checking it** — a complete list with a partial inspection still yields an overstated count. Re-checking the items you already had is a different operation again, not a more careful version of either.

- **Is it the whole result, or the part that arrived first?** A partial result licenses no direction, and hedging it does not fix that. Measured 2026-09-02: the first band of a four-band experiment showed a lever helping where prior work said it hurt; two sessions independently hedged and then stated the direction anyway. It reversed on the full table. **The hedge travelled less far than the direction did.** Report the partial number if it is useful; do not attach a reading to it, because the reading is what gets quoted.

The two failures compose, and the composition is the one to watch for: a number that is a configuration artifact **and** unreadable by the next person reads exactly like a hard-won result, because nobody can check it. Verify the capture path end to end on one case before running anything at scale, and quote the command that produced the number rather than the file it landed in.

This is the evidence-side twin of the guard rule above: there, a check that cannot read its input reports a safety it never established; here, a citation that cannot be opened reports an observation nobody made.

## Name the question your check answers, not the one you asked

**A check that runs, succeeds, and answers an adjacent question is more dangerous than one that fails**, because it is reported as having settled the thing it did not settle. Most instances below are from `matsengrp/phyz` (2026-09-06 and 2026-09-11) and read as a clean result at the time. **Two fire the other way, as a false ALARM**, and the second of those is worse than any wrong zero here: **an alarm that mimics the exact failure you are hunting prompts action rather than closing a question**, so it costs a wrong conclusion rather than a missed one.

- **A tool answering about your query rather than the world.** `grep -c` on a log returned 0 and looked like data loss; the source read `` `pcp-pipeline` `` with backticks and the pattern had none. Same shape, 2026-09-11: `git ls-files` reported an artifact uncommitted while the working tree sat four commits behind `origin/main` — it answers *"is it in my index,"* not *"is it committed"* (`git ls-tree -r origin/main` answers the latter). A whole issue draft was written on the resulting false premise. **A zero, or an absence, is a statement about your pattern and your view before it is a statement about the data.** Third costume, same day: a harness reported a background build as `exit code 0` when the build had failed — the `0` was a trailing `echo`'s status. **A reported exit code describes the last command in the chain, not the one you cared about.** The conductor session caught it only because it had captured the build's own status into a named variable; do that rather than reading the chain's. **Fourth costume, and this one is environmental rather than a pattern slip: `grep` may not be `grep`.** Measured 2026-09-12 on `pax`: in a Claude Code session `grep` is a shell *function* from `~/.claude/shell-snapshots/snapshot-zsh-*.sh` routing to `ugrep 7.8.4`, and ugrep treats a **mid-pattern `$` as an anchor** where POSIX BRE and GNU grep 3.11 treat it as literal. So `grep -c 'print $NF'` returns **0** against a file containing exactly `print $NF`, while `/usr/bin/grep -c` on the same file returns 1. The pattern is not merely non-matching, it is **unsatisfiable** — 0 against every possible input. **And it corrupts the zero-based claim specifically, which is the asymmetry that makes it dangerous: a wrong non-zero count is visible on inspection, while a wrong zero reads as "verified absent" and closes the question.** Two sessions hit this within ten minutes the same hour, each searching for *shell code* (`$bc`, `$(`, `$NF`), each within one step of reporting a file's contents absent; it read as a shared human slip and was a shared tool. **Fleet tooling is made of `$`, so this fires precisely where it is most load-bearing.** Call `/usr/bin/grep` explicitly for anything with alternation, and reserve `grep -F` for a **single literal pattern** — `-F` and alternation are mutually exclusive, see the next bullet — and when a search for something you expect returns zero, `type grep` is the one-command check that the tool is the one you think.
- **Fifth costume, and it is the remedy prescribed in the bullet above.** **Alternation → `/usr/bin/grep -E`; `-F` → exactly one pattern per invocation; never read a zero from a multi-pattern `-F` probe as evidence of absence.** In fixed-string mode `\|` is a *literal backslash-pipe*, not alternation, so the probe searches for one string that does not exist and returns **0 hits, exit 1, no error**. Measured 2026-09-13 on `matsengrp/phyz`: `grep -F 'regenerate\|historical record\|re-run' experiments/CLAUDE.md` exits 1 with no output, while `/usr/bin/grep -c -E` on the same three patterns returns **3** (lines 375, 389, 624). The zero was cited as evidence that a file did not already cover a rule, in an issue proposing to add that rule — the file carried it in two places. **This correction's own remedy has not been stress-tested either**: `/usr/bin/grep -E` is right for alternation, and nobody has yet asked what *its* adjacent failure is. Writing that down is the only thing that stops this shape recurring a third time under a third guard.

- **A state observed DURING a transition is not a state — and here the instrument is right, only the timing is wrong.** The other entries in this section are checks pointed at an adjacent *question*; this one is the correct check at an adjacent *instant*, which is why "search harder" does not reach it. Three instances on `matsengrp/phyz` 2026-09-12, all inside one hour: a process reported `STILL ALIVE` that was already exiting; a `claude` process sampled at `ppid=1` two seconds into teardown, yielding the confident conclusion *"`tmux kill-window` orphans the process"* — it was gone moments later; and a `find` over a preservation directory that correctly reported an artifact absent **47 seconds before the ceremony that creates it wrote it**, yielding *"the land-time preservation step did not run."* Each search was accurate at the instant it ran, and each conclusion was false. **Before concluding anything about a system that is visibly mid-operation, sample twice.** The tell is cheap: a worker that has just merged a PR, a window you just closed, a process you just signalled — all are mid-operation by construction, and **elapsed time is what separates a transient from a steady state** (a two-day-old orphan is real; a two-second one is teardown). **And a plausible self-diagnosis that fits a known failure shape is still only a hypothesis** — the `find` above was first blamed on its own `| head -8` truncation, a real failure mode named in this very file; checking showed the match sat at line 2 of the output, well inside the limit, and the truncation was innocent. **"Sample twice" is not enough on its own, because it does not say WHEN — and the gap that kills you is inside your own turn.** Measured 2026-09-13 on `matsengrp/phyz`: a session read `state=OPEN` from `gh pr view`, ran **two further commands**, then posted a blocking comment — which landed **30 seconds after the PR merged**, advising a hold on something already done. The read was correct when it ran. **It had also been told, in as many words, that the PR was being landed right then**, so this bullet's own tell was in hand and did not fire — *a state read is timestamped, and it decays between observing and acting even when nothing warns you.* ➡ **For anything outward-facing, re-check the state in the command that acts, not in a command before it.** That is mechanical and testable, where "be careful" and "sample twice" are neither. The same session had internalised *"don't inherit fleet state from a message"* and applied it to every peer all day; **the form that catches this is "don't inherit it from yourself either, across intervening tool calls."**
- **A filename match that was a comment.** `grep -rl converge_rung` hit a file that only *mentioned* the script in prose. Twice more the same day, on unrelated code. **The filename is not the signal; the call is.**
- **The check whose reassuring output is its own failure signal** (2026-09-11). Certifying that a rebase preserved reviewed content, `git diff <old-head> <new-head>` was reported as empty and read as "content unchanged." It was not empty — and an empty result there would have meant *the rebase never happened*, since the tree must gain whatever the new base added. Across a rebase the tree is **supposed** to change, so only patch-vs-patch (`git diff <base>...<head>` on each side, then diff the two patches) isolates your own change, paired with `git merge-base --is-ancestor` to distinguish a rebase from a re-point. **When a check's pass condition is indistinguishable from its failure condition, it is not a check** — and this one was being used to certify a gate.
- **A detector's negative result is not evidence until the detector is shown to fire.** Measured 2026-09-11: a leak-fix PR passed under `-Doptimize=ReleaseSafe` with zero leak reports, which on its own established nothing — that repo's default `ReleaseFast` disables leak detection outright, so a wrong optimize mode, a stale cache or a genuinely clean tree all render identically. The conductor session swapped the pre-fix source back in against the same tests and got `exit 1, 35/35 passed, 7 leaked`, matching the reviewer's independently measured 7; only then did the zero mean something. Generalizes to any detector whose **negative** is the pass condition — sanitizers, `expectError` paths, "no diff", "no hits", "no leaks". **Pair the pass with one run you expect to fail.**
- **The weaker test on the load-bearing example.** Two commit hashes were checked for existence — one against the local clone *and* the API, one against the local clone only. The second was the one carrying the argument, and it did exist. **Whichever example your conclusion rests on gets the strongest check, not the first one to hand.**

- **A comparison that matched on the container, not the content — and it fired as a false ALARM.** Verifying that a bug fix had not perturbed a search trajectory, committed `.gz` artifacts were compared byte-for-byte across two sweeps and returned `DIFF` on 3 of 3 sampled files; `git show <sha>:<path> | zcat | md5sum` gave **24/24 identical** on the same files (measured 2026-09-13 on `matsengrp/phyz`). **gzip records the SOURCE FILE's mtime in a 4-byte header field** — measured on gzip 1.12: `gzip -c f` and `gzip -c < f` both write `f`'s mtime (gzip `fstat`s the stdin fd), a true pipe writes `0`, and `gzip -n` suppresses it. **No normal path writes the time of compression**, so this is a property of the *inputs*, not of when you ran the tool: two compressions of one file are byte-identical, and two files with identical content but different mtimes are not. The two sweeps each wrote their trees fresh. Same shape measured for **tar and zip**; other container formats with embedded metadata are likely but untested here. ➡ **Decompress, normalise, or compare the thing you are actually claiming about** — and note the remedy follows from the mechanism only if you state the mechanism right: "embeds the time of compression" would send a reader to *"run both compressions quickly,"* which is a false-determinism trap rather than a fix. This is one of two false-alarm entries in this section, and the only one where the alarm is **the exact signature of the defect being hunted**.

The constructive form is a **discriminating filter**: filter on the property the claim needs, not on the name. Auditing which scripts inherited a defect, `grep -l -- '--model'` returned **123** files and was useless; requiring a script to *construct* a `.model` path **and** pass `--model` cut it to **15**, and reading those 15 cut it to **3**.

**A mitigation for a measurement trap has its own failure mode. Ask what it is before you write the mitigation down as a rule.** The `grep -F` entry above is not a sixth instance of carelessness — it is produced **by the mitigation for the fifth**, and it fires on someone who is *complying* with the rule. A reader who has internalized "use `-F`" cannot catch it by being more careful, because care is what put them there. That is what makes it unlike every other entry in this section, all of which are slips. A remedy that is safe for the case that motivated it can be wrong for the adjacent case, and it will be applied to both. **The tell that this has happened is a rule that is cited rather than checked.**

**Before reporting a check as settled, state which question it answers.** If that sentence is narrower than the claim, the check has not been run yet.

**A self-correction is a claim like any other and inherits no credibility from being a correction — check it against the same evidence you would demand of the thing it overturns.** Measured 2026-09-13: a session's stdin-gzip test returned SAME across a `sleep 1.1`, which already ruled out a time-of-compression field, and was read as confirming one; the session then wrote that it had caught the error *"by dumping header bytes rather than trusting the hash,"* inverting its own data and dressing it as a methodological win. **The retraction was more confident than the claim it replaced and had been checked less.** A correction arrives wearing the authority of having already been wrong once, which is exactly why it gets waved through.

**A failure that relocates under your intervention is telling you the intervention changed more than one thing.** Every number can be internally consistent and agree across arms; what does not fit is *which assertion* they belong to — and that is detectable when nothing else is. Twice in `matsengrp/phyz`, months apart, the hidden variable was **upper-CLV state, which the setup produces but does not name**: #2246's attempt to compute fresh uppers on the round-start topology "reproduced a *separate*, pre-existing defect instead of closing the gap"; and 2026-09-11, a test harness pinning branch lengths via `@memcpy` + `computeFullTraversal()` (the lower pass only) made the original assertion pass and a later one fail, in both arms, until `computeFullUpperTraversal()` restored the single-variable condition. **Whoever designs the isolation names the variable they think matters, and the naming is itself an untested assumption** — reconstruct from what the setup actually produces, not from the part of it you were thinking about.

## Before writing a correction or a unification

Three checks, each answerable in about a minute by someone who does not yet understand the finding — which is what makes them usable, since motivated correction and over-unification both happen under time pressure.

- **A correction that reduces a previously-reported quantity to *no* information deserves a second look before it's written.** Debunking has its own momentum: before recording the stronger retraction, check whether a weaker, still-true claim survives. A count found to be guaranteed in direction by construction is not thereby guaranteed in magnitude — "carries no information" is a more quotable sentence than "carries less than it appears to, in this specific way," and only one of them is usually true.
- **Before accepting a critique of a result: would this objection have been raised if the result had come out the other way?** This separates a validity critique from moving the goalposts, and pre-registration does not — pre-registration protects against choosing a lens after seeing the numbers, not against a measurement having been confounded. "The median is -5.4, so let me find a weighting that shrinks it" fails the test. "The two engines did 13x different amounts of work, so the quantity the rule was applied to may not be the quantity it was designed to judge" passes it — that would be worth stating at +5.4 exactly as much as at -5.4.
- **Two checkers agreeing means nothing if both tested the same sub-claim.** Independence of the *checker* is not independence of the *check*. Measured 2026-09-11: a "this count desyncs silently" finding was confirmed by a second session working from its own clone — which verified, correctly, that no test guards the count. Neither checked whether the count described the array the change touched. It did not; the finding was a false positive, and the worker who refused to act on either session's number caught it by asking a different question (*which array does this comment describe, and which does the new key enter?*). **Before treating agreement as corroboration, name the sub-claim each party actually evaluated.**
- **Before counting a measurement as corroboration: is it the same artifact under another name?** Independence must be established, not inferred from arriving by a different route. Measured `matsengrp/phyz` 2026-09-11: a PR reported a cross-engine offset as a *fifth* tree confirming a four-tree band; the tree it measured **was** one of the four, extracted to a new filename under a different experiment's directory, and the figure re-derived one of that band's own four measurements. Proximity did not help — the author had run `git show` on that exact file hours earlier and had amended the issue body naming it. The check is not *"does this number have a path"* but **"does this path differ from the paths of the things it is said to confirm"** (same family as `CONTINUATION-369.md`'s trap 1, three cluster IDs one character apart). And once such a claim is retracted, **grep the whole PR for the claim's subject — not the document you edited, and not the wording you changed.** Both surviving restatements sat in **summary layers** — a forward reference, and the repo's experiment index — which paraphrase rather than quote, so they are invisible to a wording-keyed grep and are the most-read surface.
- **Before merging two findings into one story: do their remedies land in the same subsystem?** A shared *symptom* is not a shared *mechanism*, and the remedy test is the cheap tell. Two failures both presenting as "far less topology search than the configuration implies" were one search that ran and was cut short by an adaptive stopping rule and one that never started because the tree handed to it had immovable branches — fixes in different subsystems, so not one pattern, and presenting them as one invites a single fix that addresses neither. "Two independent defects with a common symptom" is still a strong claim and a more useful one.
